Target device: Xiaomi 14T Pro (MediaTek Dimensity 9300+, Immortalis-G720 MC12, ARM64, Vulkan-capable, Android 14+).  
Goal: Native Android port of the existing recompilation project (i960 recompiled to native + MAME board code + SDL3 host). Bring your own vf2.zip. No ROMs included.

### Module 2 – Codebase Analysis for Android
Status: Complete (2026-10-17) — dependency map + Android findings recorded; no code changed.  
Notes:
- **Layers:** `src/core` MAME shim (i960 device, TGP) → `src/rec` i960 recompiler (SLJIT JIT at start-up) → `src/machine` Model 2A board (video, smooth, SCSP) → `src/host` SDL3 host (`main.cpp` 3318 lines, menu/RmlUi, scene sync) → `src/gpu` 3D (Metal / SDL_GPU). All pure C++20 except the two backends below.
- **Very portable:** only **23** platform ifdefs in all of `src/` — `sysinfo.cpp` (18, Windows/macOS/Linux), `main.cpp` (4), `d3d11_map.cpp` (1). Android will fall into the `__linux__` branches (works: `uname`, `/proc`).
- **Desktop-only code (all auto-excluded on Android):** `src/gpu/gpu3d_metal.mm` (Apple Objective-C++/Metal); `src/host/d3d11_map.cpp` (Windows, `#ifdef _WIN32`, compiles to a no-op TU elsewhere); `#include <SDL3/SDL_main.h>` in `main.cpp` is `_WIN32`-only.
- **GPU path:** Makefile picks backend by `$CXX -dumpmachine` — "apple"→metal else **sdlgpu**. Android toolchain prints `aarch64-unknown-linux-android26` → **SDL_GPU is selected automatically** (main.o gets `-DVF2_GPU3D_SDL=1`). `gpu3d_shaders.h` ships both `*_spv` (SPIR-V) and `*_dxil` (DXIL); Android/Vulkan uses SPIR-V. The d3d12→vulkan retry logic in `main.cpp` is Windows-centric but harmless. (Shader formats confirmed at Module-1 SDL build: GPU drivers: vulkan.)
- **JIT exec memory (key risk):** SLJIT detects aarch64 automatically. Its default allocator (`sljitConfig.h`: `SLJIT_EXECUTABLE_ALLOCATOR=1`, PROT/WX = 0) uses `mmap(PROT_READ|WRITE|EXEC, MAP_ANON)` — W+X. Android usually allows anonymous execmem, but if SELinux/OEM blocks it the recompiler fails and `main.cpp` silently falls back to the **very slow interpreter** ("no executable memory?"). Mitigation if needed: build SLJIT with `-DSLJIT_WX_EXECUTABLE_ALLOCATOR=1` (uses mprotect, avoids shm_open). Verify on device.
- **Storage:** `SDL_GetBasePath()` on Android = `"./"` (app cwd `/`) → **`find_assets()`/`program_folder()` won't find `assets/`** — needs an Android branch + assets packaged in the APK. `SDL_GetPrefPath()` = `Context.getFilesDir()` (app-private, writable, **no permission**) → `settings.ini`, NVRAM, `log.txt`, screenshots land there safely as-is.
- **ROM input:** `SDL_ShowOpenFileDialog` **is** implemented on Android (SAF via `Android_JNI_OpenFileDialog`); `OPENFOLDER` is unsupported. So the first-launch picker can work; verify the returned path is usable (SDL's Android impl copies to a readable path).
- **Input/audio/threads:** SDL gamepad + keyboard already; touch overlay + gamepad mapping is Module 6. Audio = `SDL_OpenAudioDeviceStream` S16 stereo @ `SOUND_RATE` 44100 (AAudio/OpenSLES OK). Threads via `std::thread` (`parallel.h`, up to 11 workers) — `sysinfo::tune()` is Windows-only; big.LITTLE tuning optional later.
- **Build:** Makefile sets `RENDER_FLAGS` (x86 `-mfma`) only when the user passes it — must stay off for aarch64 (pixel-exactness vs MAME isn't a target on Android). Module 3 will use Gradle+CMake, reusing the source lists.
- **ARM64 readiness: good.** No x86-only code paths in the game/machine/recompiler; the platform layer is small and additive.
- **Carry into later modules:** (3) SDL_main on Android + SDL/SLJIT build flags; (4) assets branch + storage/lifecycle; (5) verify Vulkan SDL_GPU on device; (6) touch overlay; (8) ROM picker/placement.

### Module 4 – Host Layer Port (SDL3 + Lifecycle)
Status: Complete (2026-10-18) — host runs on Android: SDL entry point, APK assets, lifecycle, ROM picker. Desktop build unaffected.  
Notes (all changes in `src/host/main.cpp` unless noted):
- **Entry point:** `<SDL3/SDL_main.h>` is now included on Android too (`main` → `SDL_main`, provided by `SDLActivity`). `libmain.so` exports `SDL_main` (verified with `llvm-nm -D`); it still exported the plain `main` at the end of Module 3.
- **Assets:** Android keeps them inside the APK, where only SDL can read them, while the game and RmlUi open files with plain `fopen`. `find_assets(data)` now copies the APK's `assets/` tree once into `<files>/assets` (`SDL_EnumerateDirectory` + `SDL_LoadFile`, which do reach APK assets) and hands that real folder to the menu and to `load_backgrounds` — so `menu.cpp`/`backgrounds.h`/RmlUi needed no changes. The desktop lookup (beside the program / `../../assets` / cwd) is unchanged.
- **Lifecycle:** `SDL_EVENT_WILL_ENTER_BACKGROUND` pauses the sound and sets a new `suspended` flag (folded into `stopped`, so no frames run); `SDL_EVENT_DID_ENTER_FOREGROUND` clears it, resets the clock (missed frames aren't run at once) and resumes the sound.
- **ROM picker:** Android's file dialog returns `content://` URIs, which `fopen` cannot read (SDL documents this). `first_launch()` now copies the chosen set through `SDL_LoadFile` into `roms/vf2.zip` and reads it back as a plain file; the desktop path is untouched.
- **Storage/logging:** no change needed — `SDL_GetPrefPath()` is the app-private files dir (writable, no permission), so `settings.ini`, NVRAM, `log.txt` and screenshots already land there.
- **Build (`android/app/build.gradle`):** `useLegacyPackaging = true` stores the libraries compressed (debug APK ~20 MB instead of ~53 MB; Android unpacks them at install) — one line to revert if the uncompressed/aligned layout is preferred. A `clearPackagedApks` task deletes the APK before `packageDebug`: AGP's incremental packaging otherwise rewrites only changed entries and never truncates, leaving the previous `libmain.so` behind as orphaned bytes that grew the APK by a library's worth on every native rebuild (and, when deleted mid-task, produced a one-entry APK).
- **Verified:** `./gradlew :app:assembleDebug` → APK 20.5 MB, 24 entries (`libSDL3.so`, `libmain.so`, manifest, dex, 12 assets), debug signature valid, and stable across incremental native rebuilds; desktop `make build/bin/vf2` still builds and links.

### Module 5 – Graphics (Vulkan / SDL_GPU)
Status: Complete (2026-10-18) — the SDL_GPU path is already Android-correct; added a ROM-free way to check the GPU 3D against the CPU, and verified the surface/swapchain, orientation and refresh-rate handling. Device-only checks listed at the end.  
Notes:
- **Shader format:** chosen at runtime from `SDL_GetGPUShaderFormats(m_dev)` (`gpu3d_sdlgpu.cpp:80`), SPIR-V preferred → Android/Vulkan gets the SPIR-V set. Shaders are compiled for `-fspv-target-env=vulkan1.0` (`tools/gpu/shaders.sh`), use only 32-bit ops, no `groupshared`, ≤8x8x64 workgroups, `rgba8` storage images → mobile-safe.
- **New `tools/gpu3dbench.cpp`** (`make gpu3dbench`, not in `all`, like gpu3dcmp): the GPU's 3D against the CPU's from the made-up bench scene (`model2_video::bench_make`) — **no ROM needed**, so it runs anywhere. It mirrors the game's own check (`main.cpp` `g3_verify`: render scale = scale * aa, capped at 8x; `read_picture` vs `bench_cpu`, same ±8/1%/5% thresholds), so each line's OK means Auto would keep the GPU on that driver. Uses a minimal link (model2_video + model2_smooth + mame_shim + gpu3d back end), no ROM/rec/68000.
- **Result on the host's Vulkan (RADV, SPIR-V), 1500 polygons, every scale 1-4 × AA 1-3 (496x384 … 3968x3072), exact and fast — all OK:** coverage differs in ≤83 of up to 12.1 M pixels (≤0.0007%), colours agree to ~99.974% (≈0.026% of pixels off by more than 8, well inside the 1% the game keeps), max channel difference 255 in a handful of texel-rounding pixels. GPU is quicker at the sizes the game uses (1984x1536: 8.7 ms vs the CPU's 9.4; 496x384: 0.5 vs 1.4) and level at the 8x maximum (43 vs 36 ms at 3968x3072).
- **Surface / swapchain:** SDL3's Vulkan backend already handles Android's surface loss — on `VK_ERROR_SURFACE_LOST_KHR` it flags `needsSurfaceRecreate`/`needsSwapchainRecreate` and rebuilds on the next acquire, and recreates the swapchain on `VK_ERROR_OUT_OF_DATE_KHR` (`third_party/sdl3/src/gpu/vulkan/SDL_gpu_vulkan.c:10242-10262`, `:10917`). The host's own recovery (`RENDER_DEVICE_RESET`/`RENDER_TARGETS_RESET` → textures lost) is unchanged, and Module 4 already stops presenting while backgrounded.
- **Orientation:** the manifest's `sensorLandscape` + `configChanges` (`orientation|screenSize|screenLayout|…`) mean a rotation does **not** restart the activity/emulator; SDL reports the new surface size and the host reshapes on `SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED`.
- **Refresh rate:** on Android SDL reports the panel's rate (`SDLSurface.java` → `nativeSetScreenResolution(..., getRefreshRate())` → `Android_ScreenRate`, and `SDL_GetCurrentDisplayMode` returns the same desktop mode), and the host's smooth-motion spare passes use it, capped at `min(240, hz)` (`main.cpp:2844`) → 120/144 Hz panels are used. SDL3 never sets `Surface.setFrameRate`, so Android's own frame-rate matching decides the surface rate; forcing it would mean editing SDL's verbatim Java copies — not done (see below).
- **Fallback (unchanged, already correct):** SDL_GPU renderer won't start → `SDL_CreateRenderer(win, nullptr)` (GLES2 on Android) + the CPU's 3D; SDL_GPU's 3D won't build or fails its check → the CPU's 3D on the SDL_GPU renderer.
- **No host changes were needed** for any of the above; only the new tool + its Makefile target were added. Desktop `build/bin/vf2` still links and the APK still builds (20,560,719 bytes, 24 entries).
- **Still to prove on the device:** SDL_GPU compute (storage buffers/textures) on the Immortalis-G720; the Auto check's verdict with the game's own textures; and whether Android gives the surface 120/144 Hz (if it sticks to 60, `Surface.setFrameRate` in the Java copy is the fix — a change to SDL's files, so only with the player's agreement).

### Module 7 – Audio
Status: Complete (2026-10-18) — the audio path needed no port beyond one Android hint: the SCSP's own 44100 Hz stereo pairs go straight into SDL's AAudio stream; added a ROM-free check of the host's own audio path, and confirmed background/focus/output changes are SDL3's own. Device-only checks at the end.  
Notes:
- **The path (verified, not assumed):** the SCSP makes its stereo pairs by the board's clock (`model2a.cpp:2965`'s `sample_index`), the host pushes each frame's sound into one `SDL_OpenAudioDeviceStream(DEFAULT_PLAYBACK, {S16, 2, 44100})` stream (`main.cpp:1913`), and SDL converts/serves them to the device. AAudio asks for I16 and almost always a 48000 Hz device, so SDL resamples 44100→48 k itself (both the stream's and the device's real formats are printable — the new tool does). The queue's unit is **input** bytes (SDL's `SDL_GetAudioStreamQueued` docs/source), so the host's pacing keeps its meaning at any device rate/format: `frame_bytes` (`main.cpp:1935`), `QUEUED` 3.5 (`:1936`), the 300 ms stall wait (`:2805`, when the device stops taking sound) and the 1% trim all still measure the same sound.
- **New `tools/audiocheck.cpp`** (`make audiocheck`, not in `all`, like gpu3dbench/touchcheck): the host's own audio path with no ROM — the same stream, the same 1/57.52 s frames and low-queue catch-up, and a tone (440 Hz left / 660 Hz right, -14 dBFS) to hear the phone's speakers by. It prints the driver, the device's real rate/format and buffer, the SDL conversion, the queue band in ms and the **lag** (queue + device buffer), then checks: the pause freezes the queue (exactly what Android's backgrounding and the menu do), a resume drains it, the queue stays under the host's 300 ms, and the device plays at the wall clock's rate. On the host's PipeWire: a queue of 26-85 ms across runs (63 ms average in the last one — the host's 3.5 frames) with 53-105 ms of lag and a 23 ms device buffer, 100% of the clock played; `SDL_AUDIODRIVER=dummy` and `=disk` pass too (disk writes `sdlaudio.raw`; its 440/660 Hz tones verified by FFT), and `AUDIOCHECK_FLOOD=1` (sound made at twice the clock, as a stalled device would see) does fail the 300 ms check — the check is not vacuous.
- **Background, focus loss, output changes: SDL3's, nothing of ours.** Android's onPause pauses the *physical* AAudio device and onResume restarts it (`SDL_androidevents.c:99-108`), on top of the host's own pause on `WILL_ENTER_BACKGROUND` (Module 4) — the two are balanced by `sound_paused`, so a menu-paused stream isn't double-paused. An AAudio error (a disconnecting device) is flagged by SDL's error callback and the stream recovered/reopened (`RecoverAAudioDevice`), and a logical device opened as the default migrates to the phone's new default output (`SDL_audio.c:2418-2463`): headphones and Bluetooth coming and going are SDL's business.
- **One change** (`src/host/main.cpp`, 5 lines): `SDL_SetHint(SDL_HINT_AUDIO_DEVICE_STREAM_ROLE, "Game")` under `#ifdef __ANDROID__` before the stream opens. AAudio reads the hint as the stream's usage (`AAUDIO_USAGE_GAME`); unset, the sound is declared as the system's default for media, which is where Android's own effects (an equaliser, ducking) and its game mode look. SDL's other backends (PipeWire) already default to "Game" themselves, and WASAPI's use of the hint is compiled out — so this changes Android only. SDL's own Android defaults are left alone: low-latency AAudio (`SDL_ANDROID_LOW_LATENCY_AUDIO`, on) and a 20 ms callback buffer / 40 ms capacity.
- **Latency:** the host's queue (~61 ms) plus the device's own buffer is the lag; on the host that measured 53-105 ms. On the phone AAudio's 20 ms callback (40 ms capacity) sits under it, so expect roughly 80-100 ms at defaults. If that proves too much once it can be heard, the knobs are `SDL_HINT_AUDIO_DEVICE_SAMPLE_FRAMES` (a smaller device buffer: underrun risk on a loaded phone) and a smaller `QUEUED` — both **parked** until the phone can be judged; `SDL_ANDROID_LOW_LATENCY_AUDIO=0` is the reverse knob if a phone's low-latency path sounds flat.
- **Verified:** host `build/bin/vf2` still links; APK builds (20,567,831 bytes, 24 entries); `strings` on its `lib/arm64-v8a/libmain.so` shows both `SDL_AUDIO_DEVICE_STREAM_ROLE` and `Game`, so the hint is really in the phone's build.
- **Still to prove on the device:** that the music, effects and voices come out of the phone at all, and how the SCSP's reverb sounds through its speaker/headphones (needs the ROM — the game itself is the test, `VF2_PACE_LOG=1` prints the queue every 60 frames); the queue and lag there; returning from a phone call or the background; headphones/Bluetooth switching mid-game; and whether 20 ms buffers underrun on the Dimensity 9300+.

- **Android's performance hints (ADPF), `sysinfo::perf_hints_*`** — a hint session over the threads a frame's work runs on (this thread + `row_pool`'s workers, `worker_tids()`), with the frame's own `1/FRAME_HZ = 17.39 ms` as its target, and the work each pass really took (`w / due`, the loop's own measurement) reported back. That is the API meant to stop exactly the throttling the two notes warn about, and the counterpart of `sysinfo::tune()`'s Windows power throttling. The calls are reached through `dlopen("libandroid.so")`/`dlsym` rather than by name: they are Android 13's (API 33, `__INTRODUCED_IN(__ANDROID_API_T__)`), and this build serves Android 8 (minSdk 26), where the library has no such symbols and a direct call would not link. Below Android 13, or if the session won't start, the game says so in one line and plays on unchanged. Display > **Performance hints** (On/Off, only where the phone has them) turns it off to compare a run, `VF2_NO_PERF_HINTS=1` does the same for one run, and the setting is kept in `settings.ini` (`perf_hints`). The render state line carries `performance hints on/off` where they exist.
